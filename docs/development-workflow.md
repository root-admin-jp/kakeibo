# 開発ワークフロー（PR とレビュー運用）

最終更新: 2026-11-07（決定 H）

## 基本方針

- `main` への変更は **必ず Pull Request 経由**とする（直接 push はしない）。
  2026-11-08 の Public 化（決定J）に伴い、main にはルールセットを設定し、
  PR 経由でない変更と force push・ブランチ削除を機械的に禁止している（決定K）。
  kakeibo では CI（api / web）の成功もマージの必須条件とする。
  また、承認1件とコードオーナー（.github/CODEOWNERS で全ファイルを本人に割当）の
  レビューを必須とし、本人以外のアカウントが作った PR は本人の承認なしにマージできない。
  リリースについても、タグの作成・更新・削除を管理者以外に禁止するルールセット
  （tag-protection）を設定し、実質的にリリース作成を本人のみに制限している。
  リポジトリ管理者（本人アカウント）は PR のマージ時に限りルールをバイパスできるが、
  直接 push はバイパスの対象外（PR は全員必須）。
  kakeibo-docs は設計書の自動同期が main へ直接 push する仕様のため PR 必須の対象外とし、
  削除・force push の禁止のみを設定している。
- PR のレビューは **Muse が担当**する。GitHub Copilot のコードレビューは
  無料プラン（Copilot Free）では利用できないため、その代替として運用する
  （2026-11-07 に本人が決定。Copilot Pro 等を導入した場合は再検討する）。

## PR の流れ

1. 作業ブランチを切って変更し、PR を作成する（本文は PR テンプレートに沿って書く）。
2. CI（API テスト / Web 単体テスト＋ビルド）が緑になることを確認する。
   大きな変更では E2E ワークフローをブランチへ手動実行して確認する。
3. Muse が差分をレビューし、結果を **PR のレビューコメントとして残す**。
4. 指摘（要修正）がある場合はブランチ側で直してから、再度 2〜3 を回す。
5. 「指摘なし（または軽微な任意指摘のみ）」＋「CI 緑」が揃ったらマージする（Squash）。

## レビュー観点（チェックリスト）

- **正しさ**: 仕様・要件との一致、境界条件、エラー処理、金額・日付など家計簿ドメインの計算
- **セキュリティ**: 認証・認可（テナント分離の破れがないか）、入力検証、秘密情報の混入、
  SQL インジェクション（MyBatis の `${}` 使用など）、依存追加の妥当性
- **テスト**: 変更に見合うテストがあるか、既存テストを弱めていないか
- **設計整合**: ADR・決定事項ログとの矛盾、設計書ジェネレータへの影響（パス変更など）
- **変更範囲**: 無関係な変更の混入、マイグレーションの後方互換性

## Dependabot PR の扱い

- 週次で届く更新 PR も同じ流れで扱う: Muse が変更内容（メジャー更新かどうか、
  他の前提を壊さないか）と CI を確認し、レビューコメントに判断（マージ / 見送り＋理由）を残す。
- メジャーバージョン更新や前提を壊す更新は、本人に確認してから扱う。

## 例外

- 緊急の修正でも PR 経由を原則とする。やむを得ず直接 push した場合は、事後に本人の確認を得て、
  理由をこのドキュメントか決定事項ログに残す。
